# Schema do Banco de Dados / Database Schema

Fonte única de verdade sobre o estado **atual** do schema do banco. Não é um changelog — para histórico, veja os arquivos em `src/main/resources/db/migration/`. Este documento descreve o que existe *agora*, depois de todas as migrations aplicadas.

## Regra de ouro / Golden rule

**Atualize este arquivo no MESMO commit em que criar uma nova migration Flyway. Nunca depois, nunca em lote.**

Esse é o hábito de maior alavancagem herdado do projeto irmão AgioMix: documentação de schema que é batida em outro momento sempre diverge do código real. Se você criar `V3__algo.sql`, a seção "Schema atual" abaixo deve refletir o resultado dessa migration antes do commit ser fechado.

## Schema atual

### Tabela `greeting_record`

Criada em `V1__create_greeting_record.sql`.

| Coluna | Tipo | Constraints |
|---|---|---|
| `id` | `BIGINT` | `PRIMARY KEY`, `GENERATED BY DEFAULT AS IDENTITY` |
| `name` | `VARCHAR(100)` | `NOT NULL` |
| `message` | `VARCHAR(255)` | `NOT NULL` |
| `created_at` | `TIMESTAMP` | `NOT NULL DEFAULT CURRENT_TIMESTAMP` |

Observações:
- Tabela de exemplo/ensino do template original; não segue ainda o padrão completo de colunas de auditoria (`ativo`, `atualizado_em`, `desativado_em`) descrito no checklist abaixo — isso é aceitável para o registro de exemplo original, mas **novas tabelas devem seguir o checklist completo**.
- Sem soft delete: é um registro de demonstração, não uma entidade de negócio.
- Sem índices adicionais além da chave primária — volume e padrão de consulta não justificam nenhum até o momento.

### Tabela `task`

Criada em `V2__create_task.sql` — recurso de referência que demonstra o checklist completo abaixo (auditoria, soft delete, concorrência otimista).

| Coluna | Tipo | Constraints |
|---|---|---|
| `id` | `BIGINT` | `PRIMARY KEY`, `GENERATED BY DEFAULT AS IDENTITY` |
| `title` | `VARCHAR(200)` | `NOT NULL` |
| `status` | `VARCHAR(20)` | `NOT NULL` (enum `TaskStatus`: `OPEN`, `DONE`, `CANCELLED`) |
| `active` | `BOOLEAN` | `NOT NULL DEFAULT TRUE` |
| `created_at` | `TIMESTAMP` | `NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| `updated_at` | `TIMESTAMP` | `NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| `deactivated_at` | `TIMESTAMP` | nullable |
| `version` | `BIGINT` | `NOT NULL DEFAULT 0` — concorrência otimista (`@Version`) |

Observações:
- Soft delete real: `DELETE /api/v1/tasks/{id}` faz `active = false` + `deactivated_at = now()`, nunca `DELETE` físico.
- Guard de status terminal: `complete` e a desativação são bloqueados se `status` já for `DONE` ou `CANCELLED` (`TaskOperationException` → 422) — ver `backend.agent.md`.
- Sem índice além da PK: volume de exemplo didático não justifica nenhum ainda; se o projeto crescer, `idx_task_status` é candidato natural para listagens filtradas por status.

## Checklist de migration

Use esta lista antes de escrever qualquer `V<n>__descricao.sql` novo.

### Nomenclatura
- Arquivo: `V<n>__descricao_curta.sql` — `V` maiúsculo, dois underscores, descrição em snake_case
- `<n>` é sempre o próximo número sequencial livre; nunca reutilize ou pule números já usados
- Nome de tabela e coluna em `snake_case`, consistente com o idioma escolhido para o projeto (mantenha um só — não misture português e inglês na mesma base)
- Se o projeto adotar nomes em português (como o AgioMix faz), mantenha o Kotlin em inglês e use `@Column(name = "...")` / `@Table(name = "...")` só para o nome de banco

### Colunas de auditoria obrigatórias em toda entidade de negócio nova
```sql
ativo         BOOLEAN      NOT NULL DEFAULT TRUE,
criado_em     TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
atualizado_em TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
desativado_em TIMESTAMP    NULL
```
(Ou os nomes em inglês equivalentes — `active`, `created_at`, `updated_at`, `deactivated_at` — se o projeto adotar inglês no banco. O importante é ter as quatro colunas, não o idioma.)

### Soft delete
- Entidades de negócio relevantes (aquelas com histórico/auditoria importantes) nunca sofrem `DELETE` físico
- Desativação é sempre `ativo = FALSE` + `desativado_em = NOW()`
- Toda query de listagem deve filtrar `ativo = TRUE` quando fizer sentido para o caso de uso

### Concorrência otimista (quando a entidade sofre escrita concorrente)
```sql
versao BIGINT NOT NULL DEFAULT 0
```
```kotlin
@Version
val version: Long = 0
```
Conflito de versão deve mapear para HTTP 409 no controller/exception handler.

### Backward compatibility
- Nunca modifique uma migration já aplicada — sempre crie a próxima (`V(n+1)`)
- Nunca faça `DROP COLUMN` no mesmo deploy em que o código passa a depender da nova estrutura; primeiro pare de usar a coluna antiga no código, depois remova em uma migration seguinte
- Nova coluna `NOT NULL` em tabela com dados existentes exige `DEFAULT`, ou uma migration em duas etapas: adicionar nullable → backfill → alterar para `NOT NULL`
- Renomear valor de enum armazenado como `VARCHAR`: crie uma migration com `UPDATE tabela SET coluna = 'NOVO' WHERE coluna = 'ANTIGO'` — nunca dependa só da mudança no código

### Valores monetários
- Sempre `NUMERIC(19,2)` (ou `NUMERIC(19,4)` se a precisão exigir) — nunca `FLOAT`/`DOUBLE PRECISION`

### Quando criar um índice
- Toda coluna de chave estrangeira (`*_id`) usada em filtro ou join recorrente precisa de índice dedicado: `idx_<tabela>_<coluna>`
- Índice composto quando a query real filtra/ordena por mais de uma coluna junta: `idx_<tabela>_<coluna1>_<coluna2>`
- Índice parcial (`WHERE ...`) quando a consulta mais comum sempre aplica o mesmo filtro fixo (ex.: apenas registros ativos, ou um subconjunto de status)
- Não crie índice especulativo sem evidência de padrão de consulta — simplicidade primeiro, otimização depois

### Depois de aplicar a migration
1. Rode a aplicação localmente e confirme que o Flyway aplicou a migration sem erro
2. Atualize a seção "Schema atual" deste documento no mesmo commit
3. Se a mudança envolver regra de negócio nova, documente também no doc de regras do projeto (se existir)
